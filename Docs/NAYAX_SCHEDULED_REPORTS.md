# Native scheduled report ingestion

The existing `refund-gmail-sync` schedule reads the approved Info mailbox's Refund Operations label and a bounded query for recent Nayax reports. Reports need no manually-added label. Threads discovered only by that provider query never enter customer intake. Exact `notifier@nayax.com` / `Nayax Transactions Report` messages take a vendor-only ingestion path before customer intake. It requires the first receiving-server Authentication-Results to be Google's aligned Nayax DMARC pass; a later sender-supplied pass does not qualify. No new schedule, mailbox, customer message, or payment operation is introduced.

The first actual file arrived September 3, 2026 at 21:09:19 UTC. It contained seven rows (two parent and five child), the 19 configured headers plus `payment_method_id_enc`, and day/month/year timestamps. Its download used HTTPS `my.nayax.com/core/reports/download` with one `file` query value. The download reference is never stored or logged. Downloading does not forward cookies or credentials, follow redirects, or accept more than 5 MiB. A missing/expired link or unknown format becomes a normal Gmail processing failure; it cannot trigger a payment retry. Header-based CSV attachments follow the same normalization. Current recipient/account/host constraints are based on observed evidence, not a claim about every possible Nayax configuration.

Machine timestamps remain local wall-clock strings. `auTime`, `seTime`, and `updated_dt` are separately preserved as the observed UTC fields. None becomes a bank settlement timestamp or inferred report period. No historical/backfill completeness is claimed, and absence of a purchase is not proof of no refund.

Some delivered Transactions Reports leave `payed_value` blank on rows that have no original-transaction link, no negative authorization or settlement amount, and no known refund status code. The importer retains those files and their row counts while keeping the paid amount unknown; those rows create no refund observation. A blank paid value still rejects the report when any of those refund signals is present, so missing data cannot hide or confirm a refund.

The native refund row linked an original transaction and carried a negative amount, but both status fields were blank. All report refund observations therefore remain non-authoritative. Even a future nonblank status is retained for review until its meaning is independently proven. An exact original/account/machine/currency/full-amount match to an existing authoritative receipt can reuse that receipt; it never creates another one. Customer-entered purchase amount is not substituted for the receipt's verified amount.

Immutable file/message/observation records deduplicate replays, delayed files, and repeated row revisions. Different evidence for the same identity remains separate; neither partial nor conflicting observations can replace a confirmed receipt or reopen payment. Exact unmatched case evidence appears once in the existing refund case activity for internal provider review. Unmatched/conflicting rows remain in the service-only observation ledger. Existing receipt operator tools remain the path for authoritative DTM confirmation and customer notice handling.

The existing Gmail health response includes a versioned report-health contract visible only to Refund Operations. It keeps four facts separate: a report-specific ingest failure, an explicitly observed Empty or failed provider run, ordinary silence after the latest file, and unknown transaction coverage. Authenticated provider-run observations are immutable, service-only, digest-bound, and limited to the recent Nayax Core distribution log; no browser polling service or new monitor is introduced. Reprocessing an old message cannot reset delivery time, while a genuinely newer delivered message can supersede an older provider-run observation even when its file contents repeat.

Only a durable report ingest failure, an explicitly observed failed provider run, or a provider file that remains un-ingested after a local 30-minute grace creates the one Refund Operations advisory. Ordinary silence and authenticated Empty runs are quiet. The advisory includes only an affected unresolved-case count, never customer details. Coverage remains `unknown` while Nayax supplies no reporting period; absence is never no-refund evidence. The contract hard-codes `paymentRetryAuthorized=false` and creates no email, notification incident, schedule, payment gate, or retry.

Verification: `npm run refunds:validate-scheduled-reports` exercises the sanitized seven-row file, strict dates/money/headers, duplicates/conflicts, receiver authenticity, linked and attachment retrieval, no raw-link storage, and network refusal. `npm run db:validate-migrations` exercises report replay, existing-receipt reuse, unknown/partial/wrong-identity cases, permission boundaries, and zero receipt/payment/message side effects. Deployment, natural ingestion and replay are already evidenced on #973. Remaining acceptance is useful outcome semantics, coverage/freshness interpretation and #971's automatic completion of a new refund; do not redeploy unchanged ingestion merely to repeat delivered work.

Native distribution logs include explicit Empty runs without a file. A gap since the latest email therefore establishes only ordinary silence, not that the provider scheduler failed. The importer cannot infer Empty from absence; it reports `explicit_empty` only from a separately authenticated, recent distribution-log observation. Unknown refund status, missing rows, explicit Empty runs, and coverage gaps never authorize completion, no-refund classification, or another payment.
